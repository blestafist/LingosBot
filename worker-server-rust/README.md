# LingosBot: HTTP-воркер на Rust

Автономный CLI для Linux. Авторизация, словарь, классы, челленджи и уроки выполняются по HTTP; браузер, .NET, база данных и Go WebUI не нужны. Существующий `worker-desktop/` не изменяется.

Используйте только аккаунт, который вам разрешено автоматизировать, с учётом правил lingos.pl.

## Установка готового Linux-релиза

В [GitHub Releases](https://github.com/blestafist/LingosBot/releases) выберите релиз `v<версия>`. Среди его файлов есть отдельные статические musl-бинарники воркера и файлы `.sha256`, **не ZIP** (ZIP-архивы относятся к desktop). Нужен Linux соответствующей архитектуры; Rust, .NET и Selenium для запуска не нужны.

В отдельном каталоге выполните в Bash (нужны `curl` и `sha256sum`):

```bash
set -euo pipefail
TAG=v1.6.0  # Замените на выбранный опубликованный тег.
case "$(uname -m)" in
    x86_64) TARGET=x86_64-unknown-linux-musl ;;
    aarch64|arm64) TARGET=aarch64-unknown-linux-musl ;;
    *) echo 'Для этой архитектуры нет готового бинарника' >&2; exit 1 ;;
esac
ASSET="lingosbot-$TARGET"
URL="https://github.com/blestafist/LingosBot/releases/download/$TAG"
curl -fLO "$URL/$ASSET"
curl -fLO "$URL/$ASSET.sha256"
sha256sum -c "$ASSET.sha256"
cp "$ASSET" lingosbot
chmod +x lingosbot
./lingosbot --version
./lingosbot --help
```

Оба скачанных файла должны находиться рядом и сохранять исходные имена до проверки SHA-256. Проверка выявляет повреждение скачивания, но не заменяет доверие к источнику релиза. `--version` и `--help` не обращаются к Lingos. Для установленного релиза используйте `./lingosbot` вместо `./target/release/lingosbot` в примерах ниже.

## Сборка и запуск

Нужен актуальный стабильный Rust:

```bash
cd worker-server-rust
cargo build --locked --release
./target/release/lingosbot --version
```

Минимальный запуск:

```bash
./target/release/lingosbot -u 'user@example.org' -p 'password' --json
```

Пароль в аргументах может быть виден в списке процессов и истории shell. Для обычного использования лучше stdin, переменная окружения или конфиг с правами `600`:

```bash
export LINGOS_USERNAME='user@example.org'
read -rsp 'Пароль: ' LINGOS_PASSWORD; echo
export LINGOS_PASSWORD
./target/release/lingosbot --json
unset LINGOS_PASSWORD
```

По умолчанию — **один урок в каждом найденном классе**, без намеренных ошибок и искусственных пауз: следующий ответ отправляется сразу после подтверждения предыдущего, как в C# HTTP-версии. Лимит времени запроса — 30 секунд, всего запуска — 900 секунд.

## Настройки

Конфиг читается только из явно выбранного источника; воркер ничего не создаёт и не сохраняет. Файл [config.example](config.example) содержит JSON без секретов:

```bash
cp config.example config.json
chmod 600 config.json
./target/release/lingosbot --config config.json --json
```

Источники взаимоисключающие: `--config PATH` (синоним `--run-config PATH`), `--config-json JSON` и `--config-json-stdin`. Последний читает один JSON-объект из stdin **до EOF**, поэтому отправитель должен закрыть поток. Для передачи секретов в конфиге предпочтителен stdin: в отличие от `--config-json`, содержимое не попадает в аргументы процесса. Например, если `private-config.json` доступен только владельцу:

```bash
chmod 600 private-config.json
./target/release/lingosbot --config-json-stdin --json < private-config.json
```

Конфиг ограничен 1 MiB; `--config`/`--run-config` принимают только обычный файл. `--config-json '{"lessonCount":2}'` удобен для настроек без секретов, но его аргумент может попасть в историю shell и список процессов. Stdin не защищает содержимое от самого отправителя или получателя потока.

Учётные данные можно указать как `username`/`password` либо как `credentials.email`/`credentials.password` для совместимости с C#-конфигом. Приоритет: CLI → непустые переменные `LINGOS_USERNAME`/`LINGOS_PASSWORD` → верхние поля JSON → `credentials` → значения по умолчанию. Явно пустые CLI-значения остаются ошибкой. Чтение файлов конфигурации поддерживается на Unix; на других ОС путь отклоняется до открытия устройства или канала.

Основные параметры JSON:

| Параметр | По умолчанию | Назначение |
| --- | --- | --- |
| `lessonCount` | `1` | Уроков на каждый класс, 1–10000 |
| `classLessonCounts` | `{}` | Переопределения по ключам `group:ID`; `0` пропускает класс |
| `errorsPer100Words` | `0` | Вероятность намеренной ошибки, 0–100%; отключается для Perfekcjonizm |
| `answerDelayMinMs` / `answerDelayMaxMs` | `0` / `0` | Диапазон паузы перед ответом, 0–60000 мс; `0` отключает ожидание |
| `lessonPromptSafetyCap` | `30` | Ограничение числа упражнений в уроке, 1–10000 |
| `requestTimeoutSeconds` | `30` | Таймаут запроса, 1–300 секунд |
| `maxRunSeconds` | `900` | Общий дедлайн, включая HTTP и паузы, 1–86400 секунд |

Например, `"classLessonCounts": {"group:12345": 2, "group:67890": 0}` запускает два урока в первом классе и пропускает второй. Остальные используют `lessonCount`. Старые ключи по названию поддерживаются, только если название однозначно. Общий бюджет — не более 10000 уроков.

Дополнительные CLI-переопределения: `--lessons`, `--errors-per100-words` (0–100), `--delay-min-ms`, `--delay-max-ms`, `--timeout-seconds`, `--max-run-seconds`. Полный список — `--help`.

Если старый конфиг задаёт паузы, они сохраняются. Чтобы отключить их без изменения файла, добавьте `--delay-min-ms 0 --delay-max-ms 0`. Скорость ограничивается задержкой ответов Lingos; карточки не отправляются параллельно, HTTP 429 останавливает запуск без повтора. Для пауз, например, используйте `--delay-min-ms 800 --delay-max-ms 1800`.

Для тестового сервера доступны `baseUrl` и `studentDashboardUrl`. Dashboard должен находиться на том же origin. Внешние серверы требуют HTTPS; HTTP разрешён только для loopback. `mode`, если задан, должен быть `api` или пустым. Настройки браузера игнорируются, браузерный fallback отсутствует.

## Классы и сбор словаря

`--scrape-class GROUP_ID` принимает положительный числовой ID группы, а не название класса или ID набора. После авторизации воркер проверяет принадлежность группы, при необходимости переключает её и подтверждает выбор новым dashboard, затем последовательно получает наборы и карточки. Уроки не запускаются; дневной лимит уроков сбору не мешает. Выбранная группа на сервере может остаться изменённой даже при ошибке. Файлы воркер не создаёт.

```bash
./target/release/lingosbot --config-json-stdin --scrape-class 12345 < private-config.json
```

Режим сбора сам включает JSON. Пример результата (значения условные):

```json
{"success":true,"scrape":{"class":{"title":"English","group_id":"12345"},"wordsets":[{"info":{"id":"42","name":"Basics","expected_count":1},"entries":[{"word":"house","translation":"дом"}]}]},"api_calls":5,"duration_seconds":1.2}
```

`expected_count` может быть `null`; если сервер указал число карточек, оно должно совпасть с полученным. ID классов, наборов и челленджей в JSON — десятичные **строки**, чтобы JavaScript не терял точность; `active_id` также может быть `null`. Дубли карточек при сборе сохраняются. Ограничения экспорта: до 256 наборов, до 10000 карточек в наборе и всего, до 16 KiB на строку и 1 MiB текста суммарно (включая название класса и наборов); действуют также ограничения HTTP и JSON ниже. Неполные или несогласованные данные приводят к ошибке, а не к частичному результату.

`--list-classes` после авторизации возвращает классы и их group ID из dashboard, не запускает уроки и несовместим с `--scrape-class`. Режим сам включает JSON:

```bash
./target/release/lingosbot --list-classes --config-json-stdin < private-config.json
```

```json
{"success":true,"classes":[{"title":"English","group_id":"12345"}],"api_calls":3,"duration_seconds":0.8}
```

Экспорт в Markdown предполагается на стороне WebUI; он ещё не реализован. Воркер возвращает данные JSON, а не MD.

## JSON, события и коды завершения

При обычном запуске с `--json` stdout содержит ровно один JSON-документ, без потока событий. Для скриптов ставьте `--json` первым: при ошибке CLI учитываются только флаги, распознанные до неё. `--help` и `--version` выводят обычный текст и не требуют авторизации.

Успех:

```json
{"success":true,"username":"user@example.org","words_learned":20,"lessons_completed":1,"errors_made":2,"api_calls":27,"classes_limited":0,"classes_empty":0,"challenge_snapshot":{"group_id":"12345","lessons_completed_at_snapshot":0,"available":0,"in_progress":1,"completed":0,"active_id":"42","challenges":[{"id":"42","title":"Trening","description":"Ćwicz","points":5,"status":"in_progress"}]},"duration_seconds":32.5,"message":"Lesson completed successfully"}
```

Ошибка:

```json
{"success":false,"error_code":"AUTH_FAILED","message":"Nieprawidłowy login lub hasło"}
```

| Exit code | `error_code` | Значение |
| --- | --- | --- |
| `0` | — | Запуск завершён; дневной лимит и пропущенные классы также не являются ошибкой |
| `1` | `AUTH_FAILED` | Ошибка авторизации или истёкшая сессия |
| `2` | `NETWORK_ERROR` | Сеть, HTTP-ошибка или дедлайн |
| `3` | `PARSING_ERROR` | Неполный ответ, неизвестное или неподтверждённое состояние |
| `3` | `CONFIG_ERROR` | Неверные аргументы или конфигурация |

`words_learned` — число подтверждённых правильных ответов на flashcard-упражнения, а не количество загруженных слов или показанных новых карточек. `lessons_completed` — завершённые уроки, `errors_made` — подтверждённые отклонённые ответы в завершённых уроках, в том числе намеренные; `classes_limited` и `classes_empty` — классы с дневным лимитом и пустым словарём. При ошибке частичная статистика в итоговом JSON не возвращается.

`challenge_snapshot` — последнее наблюдение dashboard для `group_id`, либо `null`; `challenges` содержит список с названиями, описаниями, очками и статусами, `available`, `in_progress`, `completed` — количества по состояниям, `active_id` — ID активного челленджа или `null`. Это **не обязательно финальное состояние**: если `lessons_completed_at_snapshot` меньше итогового `lessons_completed`, последующие уроки могли его изменить. WebUI должен безопасно отображать недоверенный текст из dashboard.

`api_calls` — счётчик HTTP-запросов, не только вызовов API: включает авторизацию, каждый отправленный запрос при переходе по redirect и попытки с транспортной ошибкой или ошибочным HTTP-статусом. Отклонённый адрес и истёкший дедлайн до отправки не считаются. Счётчик в успешном результате; при ошибке итоговый объект его не содержит.

### Поток событий

`--realtime` включает NDJSON в stdout: один JSON-объект на строку, каждая строка сбрасывается (`flush`) до продолжения работы. Он подразумевает JSON и заменяет режим единственного документа `--json`, даже если указаны оба флага. Последняя строка — итоговый успех или ошибка с `"type":"result"`; ошибка конфигурации также выдаёт такой результат, если флаг распознан до ошибки CLI. При невозможности записи потока запуск останавливается, POST не повторяется.

```bash
./target/release/lingosbot --realtime --config-json-stdin < private-config.json
```

Примеры строк, не полный протокол конкретного запуска:

```json
{"type":"http_request","api_calls":1,"method":"GET","status":200,"error":null}
{"type":"login_success"}
{"type":"lesson_answer","word":"house","correct":true,"intentional":false,"words_learned":1}
{"type":"result","success":false,"error_code":"NETWORK_ERROR","message":"HTTP request timed out; not retried."}
```

`http_request` приходит после получения заголовков или транспортной ошибки, до чтения тела; `api_calls` — текущий счётчик, `status` — HTTP-код или `null`, `error` — `null`, `timeout`, `connection` или `request`. В событии нет URL, заголовков и тела. `lesson_answer` содержит текст упражнения `word`, результат проверки, признак намеренной ошибки и число правильных ответов **в текущем уроке**. Эти слова и данные экспорта могут быть конфиденциальными: защищайте stdout, логи и получателя потока. Прогресс мог быть выдан до последующей ошибки и не означает завершения урока.

## Поведение при сбое

- Один последовательный процесс и одна HTTP-сессия; cookies и словарь живут только в памяти. HTTP-клиент использует пул соединений и keep-alive, когда сервер это допускает; GET наборов не выполняются параллельно, чтобы сохранить порядок cookies сессии.
- Ни один POST не повторяется после таймаута, обрыва, редиректа или некорректного ответа: сервер уже мог обработать запрос. Не запускайте автоматический повтор всего задания после такой ошибки.
- Другой вариант ответа отправляется только после явного отклонения предыдущего сервером.
- Смена класса и вступление в челлендж подтверждаются новым dashboard. Неполный словарь и неизвестные состояния останавливают запуск.
- Валидно пустой словарь пропускает только соответствующий класс. Дневной лимит также проверяется для каждого класса отдельно: его глобальность API не гарантирует.
- HTTP-ответ ограничен 1 MiB после распаковки gzip. HTML читается без построения DOM; скрипты, CDATA и шаблоны не используются как данные страницы. Вложенные границы SVG/MathML и их HTML-контекстов ограничены 64 уровнями; обычная вложенность HTML не требует стека. JSON отклоняет дубликаты ключей, глубину свыше 64 и более 16384 значений.
- Обнаружение классов и наборов ограничено 256 элементами каждого типа; набор — 10000 карточками (также действуют лимиты HTTP/JSON). Переходы на другой origin и системные HTTP-прокси отключены.
- Словарь ограничен 10000 уникальных пар и 1 MiB хранимого текста с учётом нормализованных ключей и индекса; одна строка — 16 KiB. Превышение лимита останавливает запуск с `PARSING_ERROR`, а не разрешает отвечать по частичному словарю.
- Воркер не пишет HTML, cookies, пароли или диагностические дампы на диск. Необработанные сообщения HTTP/JSON-парсеров не печатаются.

## Разработка

```bash
cargo fmt --all -- --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
```

Структура без пустых слоёв:

```text
src/
  main.rs                 CLI и итоговый вывод
  config.rs               настройки и проверка значений
  error.rs                стабильные ошибки и exit codes
  infrastructure/         HTTP-сессия, cookies, CSRF и HTML
  models.rs               структуры learning API
  vocabulary.rs           варианты переводов и нормализация
  lesson.rs               последовательный движок урока
  challenge.rs            состояния челленджей и Perfekcjonizm
  workflow.rs             классы, сбор словаря и запуск уроков
tests/
  unit/                   модульные тесты всех компонентов
  common/                 локальный HTTP-сервер для тестов
  http.rs                 интеграционные тесты HTTP-сессии
  cli.rs                  сквозные тесты CLI
```

Весь тестовый код находится только в `tests/`. Модульные тесты из `tests/unit/` подключаются через `#[cfg(test)]` и `#[path]`: они проверяют и приватные функции, не расширяя публичный API и не попадая в обычную сборку. Тесты не требуют аккаунта, браузера и доступа к lingos.pl.

Release-профиль использует `opt-level="z"`, LTO, strip и `panic="abort"`. [Общий workflow](../.github/workflows/ci-release.yml) при каждом push в любую ветку и PR тестирует и собирает всё (в том числе musl на native x86_64 и aarch64), но ничего не публикует. Для каждого release-бинарника проверяются ELF-архитектура, отсутствие `INTERP`/`NEEDED`, запуск `--version`/`--help` и SHA-256 через `sha256sum -c`.

Черновик релиза создаётся только при push тега `v*`, если все проверки и сборки успешны, а коммит тега входит в `main`. Описание черновика берётся из сообщения коммита тега; публикует релиз человек. Порядок описан в [Docs/Releasing.md](../Docs/Releasing.md).

Для локальной native musl-сборки нужны соответствующий Rust target и `musl-gcc`. Кросс-сборка для другой архитектуры дополнительно требует подходящего C-toolchain/linker; одного `rustup target add` недостаточно.

### Локальные измерения

Предыдущая версия `b67446a`: Linux x86_64, release, один класс, 1000 слов в словаре и 20 подтверждённых ответов; полный CLI-прогон через локальный HTTP-сервер без намеренных пауз:

| Сборка | Размер бинарника, байт | Пиковый RSS, КиБ |
| --- | --- | --- |
| GNU/glibc | 2 932 584 | 5668 |
| Статическая musl | 3 044 096 | 4968 |

На этом локальном стенде 20 ответов с прежними паузами по умолчанию заняли 26,32 с; с новыми настройками — около 0,01–0,02 с, 27 HTTP-запросов вместо 28. Основной выигрыш — удаление искусственного ожидания; реальная скорость зависит от времени ответов Lingos. Это не live-бенчмарк сайта и не замер превосходства Rust над C#.

RSS измерен через `wait4/getrusage` из маленького C-launcher, чтобы не включать память Python-сервера. Это измерение тестового сценария, не гарантия для любого словаря или TLS-соединения. Структуры реальных dashboard/wordsets проверены read-only; полный live-прогон Rust с авторизацией и ответами на lingos.pl пока не выполнен. Сборка aarch64 предусмотрена в CI, локально проверена только x86_64.

После добавления JSON-протокола размеры локальных x86_64 release-бинарников составляют 2 974 632 байт (GNU) и 3 089 184 байт (musl). Повторные замеры времени и RSS для новой версии не выполнялись.
